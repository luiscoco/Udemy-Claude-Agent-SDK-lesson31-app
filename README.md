# Claude Agent SDK · Lesson 31 · Clarifying questions

Five linked student pages, large text, actual SDK experiments and coloured code in all thirteen UML steps.

## What you will learn

- Enable and detect AskUserQuestion: Keep AskUserQuestion in an explicit tools list and route that tool name to a dedicated question handler. Normal tool permission requests belong in a separate branch. An allow entry does not provide the missing human answers.
- Present Claude’s actual questions: Parse questions, header, options and multiSelect. Claude owns the wording and choices. The host renders radio buttons or checkboxes and offers a custom Other answer without appending new SDK questions.
- Return full-text answer keys: Preserve the original questions array. Map each full question text to its selected label, joined multi-select labels or the student’s custom answer. A header or option index is not the SDK answer key.
- Compare custom text with a general reply: Other belongs in answers[question]. A general response dismisses the structured card and uses the optional response field instead. The UI supports both, and offline tests distinguish their returned shapes.
- Render optional previews: TypeScript toolConfig can request HTML or Markdown previews. Display only previews the model actually supplies. The SDK rejects certain unsafe HTML; the browser also sanitizes fragments and uses a sandboxed iframe with a restrictive content policy.
- Handle plan mode, cancellation and limits: Answer real questions before a read-only plan. Abort and timeout settle the waiting promise without inventing an answer. The UI is a local teaching sample; a long-lived production workflow may need documented deferred execution and authenticated request ownership.

## Reference topics and limits

- Question ownership: Claude generates the questions and options. The host can add an Other control to its own UI without modifying the original questions array. Questions invented by the application belong in a separate application flow.
- Answer shape: Use full question text as each key, not the short header. The app joins multi-select labels with comma-space, which the SDK supports. Custom Other text is a per-question answer; response is a general reply replacing the structured answer list.
- Question and preview limits: The question tool supports one to four questions and two to four options per question. Preview fields are optional. The configured format applies to the session but does not guarantee a preview for every option.
- HTML preview boundaries: The SDK rejects script, style elements and DOCTYPE in generated HTML previews. This UI also sanitizes allowed tags and attributes, uses a sandbox without scripts and applies a content policy that blocks external resources. Trusted wrapper CSS keeps preview text readable.
- Plan mode: The plan experiment asks an actual clarifying question before a short read-only plan. It exposes only Read and AskUserQuestion and never enables edits. A model-generated plan artifact, if attempted by the runtime, remains outside the permitted tool scope and is logged.
- Waiting versus deferred execution: This app keeps a process alive while the callback promise waits. A two-minute timeout cancels and settles it. The documented PreToolUse defer pattern is a separate design for resuming persisted sessions and is explained here without pretending it is implemented.
- Local teaching scope: The loopback server accepts one active query and checks POST origins. Request IDs are single-use; invalid or stale decisions cannot approve another request. A deployed multi-user app needs authenticated ownership and its own durable lifecycle.
- Evidence and API usage: All questions, previews and native results in the live examples come from actual SDK calls. Scripted CLI/test selections are labelled explicitly. Each query has a $0.45 SDK budget threshold, not a prepaid cap. Credentials, dependencies and all teaching media stay outside Git.
